# BaijiMind v0.1 架构决策记录（ADR）

> 对应开源项目：domain-separated-self-boot-agent-runtime
> 文档版本：v0.1 第一版 · 文档日期：2026-08-21
> 决策依据白皮书：[docs/original-2026-paradigm.md](original-2026-paradigm.md) · 完整实现计划：[docs/v0.1-implementation-plan.md](v0.1-implementation-plan.md)

本文档记录 BaijiMind v0.1 落地时确定的 17 条关键架构决策。每条决策一经确定，后续代码开发、版本迭代需遵循，不再推翻；如需修订，须另立新 ADR 并说明替换关系。

## 决策总览

## 1. gRPC 动作面（Java→Go，单向小面）

**决策**：Java 与 Go 之间唯一的内部通信通道为 gRPC，共享 `.proto` 契约作为跨语言契约唯一来源。RPC 面保持最小：`SendMessage`（发飞书）、`ExecutePlugin`（插件沙箱执行+流式回传）、`ActivatePlugin/DeactivatePlugin`（插件热加载/回滚）、`ListPlugins`（运行态对账）、`SubscribeEvents`（Java 领域事件流→Go 分发）。浏览器→Java、飞书→Go、Go→MinIO 全走 HTTP。

**理由**：跨语言契约漂移是本项目最大风险之一，一份 `.proto` 把契约钉死；Java 与 Go 的 gRPC 生态均成熟。调用面小（约 5-6 个 RPC），gRPC 不增加多少复杂度。

## 2. 数据库 Java 全 owner

**决策**：业务数据**全部**由 Java 拥有并管理，Java 是唯一事实源。`deploy/sql/schema.sql` 为唯一 DDL 来源，另配表所有权清单（`deploy/sql/ownership.md`）。

**外部进程无状态、不落业务库**：Koishi 网关（IM 协议层）与桌面采集 agent（OCR 采集）都不写业务表，只通过 **RocketMQ** 与 Java 交换消息；一切业务数据写入经 Java 落地。二者均可随时重启、替换、水平增删而不影响数据一致性。

**理由**：消除双写冲突与 schema 漂移；Java 是业务/治理/执行的单一 owner，权限与审计更易闭环；外部组件无状态化后，协议层/采集层的实现可以独立演进（换网关、换 OCR 引擎）而不触碰数据层。

## 3. 任务队列

**决策**：不引入 MQ。`exec_task` 表 + 原子领取（`UPDATE ... WHERE status='CREATED'` 乐观锁），Java worker（线程池/虚拟线程）领取执行；`claim_at+deadline` 超时回收；执行幂等可重入。

**理由**：v0.1 规模下 MySQL 表队列足够，省去一套基础设施；乐观领取天然契合"人下达、AI 领取"的语义。

> **修订见 ADR #17**：本决策「不引入 MQ」仅指任务队列本身仍用 DB 表队列（原子领取语义）；跨模块事件总线已由 #17 引入 RocketMQ。

## 4. 向量检索 = Milvus（Standalone 单机形态）

**决策**：向量检索采用 Milvus Standalone（etcd + 复用现有 MinIO 存储），本地开发可用嵌入式 Milvus Lite。Spring AI `MilvusVectorStore` 接入；**混合检索（dense+BM25，Milvus 原生支持含 RRF）**；`project_id` 作为 partition key，权限过滤按分区裁剪（index 层过滤，权限不出域）；重排（cross-encoder/rerank API）留接口，v0.1 可选。

**理由**：国内企业生产最常用的权威向量库；本项目内容规模（数十万 chunk）落在其单机舒适区；混合检索与权限过滤开箱即用。代价：资源占用比轻量向量库高，分布式部署（多组件）运维权重高——Standalone 单机形态可跑，规模大了再上分布式。

## 5. 切块策略

**决策**：结构化切块（按文档标题/章节，LangChain4j + Tika），512-1024 token + 128 overlap；聊天文本按消息/时间窗口切；元数据（项目/需求/权限域）随块存储并参与检索前过滤；embedding 模型选定后版本化，换模型需全量重建。

**理由**：对齐业内生产共识——切块策略对召回的影响大于向量库选型本身。

## 6. 流程编排 + 执行都在 Java

**决策**：JSON DAG 流程定义/审批/绑定/走查/执行一体（节点含审批门），执行节点直接走 Java 的 AI Agent 循环；容器化工作流为远期形态。

**理由**：编排=管控逻辑，留在治理域（Java）内最内聚；v0.1 用 JSON DAG 解释执行，避免容器化工作流带来的编排复杂度。

## 7. AI Agent + harness 在 Java

**决策**：LangChain4j/Spring AI 做 function-calling 循环；内置工具集（文件/git/检索/发消息/测试/gen_h5_prototype）Java 原生实现，RAG 检索进程内调用。AI 新写的插件工具走审批+版本后，注册进插件能力注册中心，**容器插件**（AI 写 Go 代码构建镜像）经 docker-java 沙箱执行（资源上限/超时熔断/无凭据/网络受限），经 HTTP 供调用。业务型插件（事件驱动，飞书小服务类比）订阅 RocketMQ 领域事件，由 Java 事件驱动宿主分发。每次工具调用落机械信号（重试/错误类别）到 `exec_task_event`（工具自省的数据口子）。

**理由**：AI agent 生态 Java 明显强于 Go，且 agent 依赖 Java 域数据（RAG/项目/审批），进程内调用省 RPC；插件沙箱交给 Docker 容器（隔离更强、语言完整、运维熟悉），Java 专注业务与治理。

## 8. IM 采集双路径：Koishi 网关 + 桌面 OCR 采集

**决策**：IM 采集分两条路径，**统一消息契约，RocketMQ 作为域间总线**。

**路径 A —— Koishi 网关（有开放接口的平台）**：飞书 / 企业微信 / 钉钉 / QQ 官方等平台，由 **Koishi**（Node.js/TypeScript，Cordis 微内核，官方适配器覆盖上述平台）承担协议翻译与收发。Koishi 部署在服务端、**无状态、不落业务库**；其插件把平台消息归一为统一 `ImMessage` 后发布到 RocketMQ，并消费出站消息回发平台。

**路径 B —— 桌面 OCR 采集（无开放接口的平台，如个人微信）**：个人微信不开放群聊接口，采用**桌面采集 agent**——截屏 + OCR 识别聊天区内容，归一为同一个 `ImMessage` 后发布到 RocketMQ。三条约束：

1. **跑在员工桌面**：员工自己的机器、自己的微信账号、**显式授权**；可随时暂停采集、查看采集日志
2. **纯 OCR**：不做 UIA 读树、不注入进程、不改协议——只截屏识别，零输入事件
3. **只读 + 剪贴板辅助**：只采集不发送；AI 生成的回复**写入剪贴板**并提示，由员工手工 Ctrl+V 发送（零模拟输入事件，规避行为检测，且天然是"AI 只提案、人执行"）

**统一契约**：`ImMessage`（platform / channelId / channelType / sender / content / attachments / timestamp + **`source`**（`koishi` | `desktop-ocr`）/**`confidence`** / **`uncertain`**）。两条路径发**同一个** `im.msg.received` 事件，下游（命令路由 / 归档 / RAG / 业务型工具）**零改动**。

**OCR 噪声显式建模**：桌面采集**必然出错**，不假设数据干净——每条消息带 `confidence`，低置信或发送者映射不唯一的消息标记为"待人工确认"，**不进命令路由**（只入归档）；切分不确定的消息（多行 / 引用 / 合并转发）标 `uncertain`。靠去重（内容哈希 + 发送者 + 时间窗，无平台 msgId）+ 置信度分级 + 人工确认 + 可重放把补救成本压下来（白皮书 §3.1.5）。

**隐私与授权**：机主同意 ≠ 群成员同意——群聊中他人发言也会被采集。约束为：**工作群白名单**（只采绑定了项目/需求的群，复用 `proj_im_config` 绑定），白名单**由服务端下发并由 BaijiMind 校验**（客户端不可自行扩权）；非白名单群不截屏；每次采集落 `audit_log`（actor=desktop-agent，delegate_of=员工），与 ADR #12「授权即边界」同构。

**不做交互卡片**：流程决策/审批统一在管理端需求流程页（标准工作流审批，类似 OA），群里可发管理端页面链接供跳转；@AI 文字指令仍走命令路由建任务/查状态。

**理由**：两类平台的可得性根本不同——有接口的走成熟网关（Koishi 适配器生态覆盖广，"新平台 = 装适配器"），没接口的只能绕开协议层（读屏是零侵入、低风险路径：不注入进程、不改协议，检测面仅为行为统计）。统一 `ImMessage` 让两条路径在下游完全同构，采集方式的差异被隔离在网关层——这正是分域思想在 IM 接入上的体现。

## 9. 密钥加密

**决策**：git ssh key、IM secret、LLM key、Milvus key 落 `sec_secret`（Java owner），AES-GCM + 环境变量主密钥加密，明文不进库；Go 需要的 IM secret 经 gRPC 下发或只读表取密文解密。

**理由**：密钥明文入库是不可接受的安全债；统一密钥表 + 加密存储，配合"Go 沙箱无凭据"（决策14）形成纵深防御。

## 10. 多企业预留

**决策**：核心表带 `enterprise_id`；v0.1 单企业部署，但结构预留多企业。

**理由**：避免二期多企业改造表结构；成本极低，收益在扩展性。

## 11. 组织可观测性（留口子，最小实验）

**决策**：v0.1 不建独立事件流/链路/指标栈。观察器所需数据直接聚合现有表（`exec_task/exec_task_event`、`flow_instance/flow_node_state`、`audit_log`、`msg_archive`），提供一个只读聚合查询接口（组织快照：任务/流程统计、tool 使用、重复模式）。完整独立可观测层（OpenTelemetry/时序库）二期观察器实验成型后再上。

**理由**：最小实验原则——先验证观察器的价值，数据落地靠现有表顺带产生，几乎零成本；机制成熟后再投入独立可观测栈。

> **修订见 ADR #17**：领域事件流由 RocketMQ 事件总线承担（观察器数据源 = 领域事件落账 + 现有表）；独立可观测层（OTel/时序库）仍二期。

## 12. 授权即边界（数据权限委托）

**决策**：谁点流程/下指令，AI 领任务后就以谁的数据权限执行。`exec_task.authorizer_user_id` 记录授权人，执行时解析其权限作用域（组织树可达域+项目/需求权限），AI 全链路（RAG 检索、内容空间、git、IM、Go 插件沙箱）都被限定在该作用域内；越权访问拒绝并审计。audit 记录 actor=AI(taskId)+delegate_of=授权人，所有 AI 动作可追溯到授权人。

**理由**：AI 无独立权限，只在人授权的边界内行动——这是"人始终是最终审批者与责任主体"在数据层的落地，是安全的根基。

## 13. 越权审计（留口子）

**决策**：授权边界的所有越权/拒绝事件由决策 12 落 audit_log（actor、delegate_of、resource、action、result=denied）。v0.1 只做审计口子：① 人审——控制台"越权审计"页查 audit_log 的 denied 记录（人/AI、授权人、时间、资源）；② AI 审——观察器最小版把"越权/拒绝统计"纳入观察报告；深度权限合规分析放二期。

**理由**：越权行为可发现、可定位是第一要务，深度分析留待数据积累后。

## 14. 接口即边界（AI 读企业内容一律经带权限接口）

**决策**：AI/工具**不直连 Mapper/表**，所有企业内容读取（内容空间、聊天归档、需求/项目、RAG 检索、git 元数据）一律经统一**内容访问接口**，接口内强制注入授权人作用域过滤，越权即拒。容器插件沙箱为**无凭据环境**，插件读企业内容只能经 Java 受限读接口（HTTP），拿不到数据库直连。接口层统一记录 actor+scope。

**理由**：权限控制不是"记得去校验"，而是结构性无法绕过——把权限做成数据访问的唯一通道，天然可审计。

## 15. 定时任务（Spring @Scheduled + Redis 分布式锁）

**决策**：所有定时任务（RAG 增量构建、任务超时回收、自举观察器周期审计）统一用 Spring `@Scheduled`，并以 **Redis 分布式锁**（Redisson RLock；Redis 已存在，零新增中间件）保证多实例部署时同一时刻只有一个实例在执行，避免重复构建/重复回收/重复报告。不引入 Quartz/xxl-job/PowerJob 等调度中间件。

**理由**：v0.1 定时任务数量少、间隔粗，Spring `@Scheduled` 足够；多实例防重复是唯一必须解决的并发问题，Redis 分布式锁顺手解决，成本最低。**注**：① 分布式事务中间件（如 Seata）v0.1 不引入——单库近全 owner（决策2）已规避大部分跨服务事务，二期出现多服务共享写场景时再按需引入；② 分布式定时任务框架（如 xxl-job/PowerJob）同样二期按需引入——v0.1 任务少，`@Scheduled` + Redis 锁即可覆盖。

## 16. 组织治理与成长模块（治理实体化）

**决策**：新增 7 个模块让组织可治理、可成长——① 中心原则管理、② 局部原则+冲突裁决、③ 组织目标与优先级、④ 治理决策记录、⑤ 组织演化史、⑥ 组织健康度仪表盘、⑦ 能力画像。全部复用生产验证过的成熟实践，无新发明：①＝策略即代码+配置版本化+流程版本化（OPA/Nacos/Flowable）、②＝K8s 多租户策略层级/事业部制、③＝OKR/Backlog 优先级、④＝ADR/RFC/合规留痕、⑤＝Git 历史/Changelog/数据血缘（聚合视图）、⑥＝DORA 指标/累积流图（聚合视图）、⑦＝技能矩阵/胜任力模型。多数为轻量实现（定义表+聚合视图+控制台页），不引入新中间件。

**理由**：让"组织"从业务功能集合成为有实体、可感知、会成长的有机体——治理有了可演化的宪法（必要多样性）、分域有了家规与裁决（§3.3）、成长有方向（OKR）、决策可追溯（ADR）、长大看得见（演化史）、失序看得见（负熵可视化）、能力有地图（技能矩阵）。这也再次印证白皮书"载体零"：这套组织规律是成熟的，不是实验性的。

**现实度分层（v0.1）**：③④（目标优先级/治理决策记录）v0.1 务实实现——本质是数据+展示，价值即时；⑤⑥⑦（演化史/健康度/能力画像）v0.1 只搭最小版聚合架子，价值靠长期数据积累；①②（中心原则/局部原则+裁决）v0.1 不实现、仅留口子——v0.1 治理规则少，给规则上版本化是过度工程；②还依赖①存在，且裁决质量长期靠人/治理锚点判断，AI 只能辅助。

## 17. 事件驱动 + CQRS-lite（RocketMQ 事件总线）

**决策**：v0.1 引入 RocketMQ（namesrv + broker，docker-compose 内置）作为跨模块**领域事件总线**。模块间「通知型/联动型」协作走事件（发布/订阅）：任务生命周期、流程节点、IM 消息命中、文档新增、审批、工具调用、LLM 用量等。写侧命令走领域模块接口（**DB 行是事实源**）；读侧 v0.1 **读写同表**，走**内容访问接口**（低层同步读取保留直接 Query，决策 14）；**读模型/异步投影留待后续**（事件已就位，届时直接加投影）；**不做事件溯源**。事件发布用**事务性发件箱**（业务表与 `event_outbox` 同事务 → @Scheduled 轮询投递 RocketMQ，Redis 锁防重复，复用决策 15 模式），消费方**幂等**（eventId 去重、可重放）。

**Topic/Tag 约定**：Topic=领域（`baimind-task` / `baimind-flow` / `baimind-im` / `baimind-space` / `baimind-boot` / `baimind-tool` / `baimind-llm`），Tag=事件类型（如 `task.completed`）；消费组按模块建，一模块一 ConsumerGroup。

**理由**：事件驱动使模块解耦、可拆分组合，新模块以订阅/发布接入而不改既有接口（对齐「容易拆分组合、写新模块简单」）；RocketMQ 提供持久化/重放/顺序，天然承载重放日志与审计（白皮书 §3.1.5 补救经济性）；v0.1 直接上真实 MQ，避免「先表行、后迁移」返工。

**替换关系**：取代 ADR #3「不引入 MQ」与 ADR #11「v0.1 不建独立事件流」中关于事件基础设施的表述；任务队列领取机制（exec_task 表 + 原子 UPDATE）不变。

**代价与对策**：新增 namesrv + broker 两个容器（部署变重，docker-compose 一键起仍成立）；消费幂等/乱序用 eventId 去重 + 顺序 topic（按需）；事务一致性靠发件箱，分布式事务中间件（Seata）仍不引入。

## 附：关键风险清单

- **并发安全**：任务领取/状态迁移必须单行条件 UPDATE（status=? 乐观锁）；执行幂等可重入。
- **契约漂移**：三处唯一契约来源——`schema.sql` + 表所有权清单、**`ImMessage` 采集消息契约**（跨语言：Java/Node/Python 三方共用）、事件 topic/tag 契约；改契约需同步更新对应文档与三方实现。
- **权限不可绕过**：AI 读企业内容只经「内容访问接口」，禁止注入 Mapper/直连表；容器沙箱无凭据。
- **沙箱隔离**：容器插件执行限定资源上限/超时熔断/无凭据/网络受限（docker-java）；不注入生产凭据。
- **密钥安全**：ssh key/im secret/llm key 只存 sec_secret 密文（AES-GCM），明文不进库。
- **超时回收**：CLAIMED 带 claim_at+deadline，超时回收重置，避免死任务。
- **本地 dev 无公网**：Koishi 用长连接收事件；流程决策走管理端页面（无需公网回调）。
- **桌面采集隐私**：机主同意 ≠ 群成员同意——群聊中他人发言也会被采集。约束：工作群白名单（仅绑定了项目的群）+ 员工可暂停/查看采集日志 + 白名单服务端下发且 BaijiMind 校验（客户端不可扩权）+ 采集落审计。企业需自定对群成员的告知口径。
- **桌面采集准确性**：OCR 必然出错且无平台 msgId——去重靠内容哈希+发送者+时间窗；`confidence` 低于阈值的消息不进命令路由（只归档）；切分不确定标 `uncertain`；靠人工确认与可重放压补救成本（§3.1.5）。
- **桌面采集被检测**：纯 OCR + 只读（零输入事件）封号风险最低；出站用剪贴板辅助而非模拟输入（社区实证：自动输入过快会触发微信退出登录）。仍需控制采集频率与运行时长，避免行为异常。
- **多企业预留**：核心表带 enterprise_id，v0.1 单企业部署但结构预留。
- **Milvus 运维权重**：Standalone 单机可跑，资源占用比 Qdrant 高，规模大了再上分布式。
- **事件可靠性**：事件发布与业务落库同事务（事务性发件箱，Redis 锁防重复投递）；消费方幂等（eventId 去重）；事件可重放，既作补救（§3.1.5 压 ρ）又作审计/观察器数据源。
